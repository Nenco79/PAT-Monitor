# capture reference measurement, 11 September 2026 (evening), second round
# NVIDIA GeForce RTX 4080, driver 32.0.16.1664
# Logitech Brio 105 carried over from the development machine
#
# **First measurement on NVIDIA.** Nobody had ever run this program on that
# vendor: the table at the top of CLAUDE.md had three columns and NVIDIA was not
# one of them. These are the numbers.
#
# **It is not compared with the Intel or AMD reports**, and cannot be: different
# scene, light, camera and encoder. Each machine is compared with itself.
#
# **This is the second round.** The first, on another USB port, is in the history
# at commit 4f1e448 — its camera delivered 14.5 fps against the 19.4 here, so its
# numbers are superseded rather than kept. What it is worth reading for is that
# two of its claims were wrong, and are corrected below.
#
#   video          782 frames, 19.4 fps, 1565 - 1568 kbit/s out of 2500 asked
#   keyframes      20, against ~20 expected with a 2 s GOP
#   profile        42e01f, one value, constrained baseline level 3.1
#   quantiser      26.1 mean, p95 30, max 38, read from the STREAM
#   audio          1993 Opus packets, 64 kbit/s, raw mode obtained
#   video delivery median 48.2 ms, p95 64.7, max 68.1
#   video in bursts  0 of 781 (0%)
#
# **The defect this item was opened for does not appear.** crbug.com/1088650's
# symptoms are keyframes in bursts and the resolution stuck at 360p. The
# keyframes are 20 against ~20 expected and evenly spaced, the stream carries one
# `profile-level-id` and it is `42e01f` — the constrained baseline we ask for —
# and the size is the one requested. What is measured is **our** encoder path,
# not a browser decoding it.
#
# **The delivery is steady**: 0% in bursts on every stream, against AMD's 32-36%
# on the video. The pairwise delivery recorded in capture-amd.txt is that chip's
# and not the pipeline's.
#
# **Keyframes on demand are honoured**, which `IsModifiable` had refused to say:
# it answers `E_NOTIMPL` here, exactly as AMD does while honouring them
# perfectly. Asked for one a second over forty seconds, the stream carried **40
# keyframes against the ~20 the GOP alone produces** — every request answered.
# The timing of each is lost with that run's verdict, for the reason two
# paragraphs down.
#
# **Both roads to the bitrate work.** By command 1379 -> 199 kbit/s within two
# seconds, settling at 435-788 with the quantiser going 25 -> 40; by rebuilding
# the encoder, 1482 -> 766 for 800 asked, `[OK]`. That is the AMD pattern and not
# the Quick Sync one, so the cheap road — the one that interrupts nothing — is
# the right one here.
#
# **B frames are refused**, `0x80070057`, so every start on this vendor logs
# `some encoder settings were not accepted`. It is a log line and not an alert,
# checked rather than assumed, and it costs nothing: `QPSlice` refuses a B slice
# outright, and the quantiser was read on all 780 frames, so that stream had none
# to refuse. The belt was refused and the braces held.
#
# ---------------------------------------------------------------------------
# THE FINDING, and it is not about NVIDIA
# ---------------------------------------------------------------------------
#
# **The resolution scale's own step kills the capture on this camera.** Asked for
# 960x528 — three quarters of 1280x720 rounded to macroblocks, which is what the
# monitor asks for when the picture has to shrink — the reader **accepted it**
# and the next read failed:
#
#     video format changed  video=960x528@30  reader=960x528  error=<nil>
#     capture interrupted, restarting  ran_for=20.693s  error="ReadSample: HRESULT 0x80004005"
#     camera opened  format="NV12 1280x720@30"
#
# That is two seconds of no picture and a capture that comes back at **full
# size**, that is, at the size the network had just been unable to carry. In the
# monitor the scale would then ask again. What happens next was measured
# afterwards — eight minutes, five requests for the same step, a backoff
# doubling to sixteen seconds and ~32 s of black picture out of 70 — and it is
# in CLAUDE.md, under the resolution scale.
#
# **It is the camera and not our code**, and the control says so: the same step,
# on the development machine's ACER HD User Facing, went through with no
# interruption at all — 669 frames, 26.5 fps, the format change clean. So a size
# the Source Reader accepts can still be one the device will not deliver, and
# `SetCurrentMediaType` answering `S_OK` says nothing about it. It is the same
# shape as an `ICodecAPI` property accepted and never applied.
#
# **And it is not the USB port, which the first round got wrong.** That header
# blamed the port for both the halved cadence and the scaling failures. The port
# was changed and `pat-diag`'s scaling block is **identical** — 960x540 and
# 848x480 still answer `ReadSample: HRESULT 0x80004005` while 1280x720 and
# 640x360 are delivered — so only the cadence moved, 14.5 to 19.4 fps. Two
# symptoms that arrived together were assumed to have one cause, and one of them
# survived the remedy.
#
# **Whether 19.4 fps is the cable or the light is still unknown.** A Brio drops
# its cadence in low light, and both rounds were taken late in the evening; the
# port moved the number by a third, which says the cable is part of it and not
# that it is all of it. It is why these numbers are compared only with
# themselves.
#
# ---------------------------------------------------------------------------
# THE INSTRUMENT, and a defect of its own
# ---------------------------------------------------------------------------
#
# **Three of these eight runs ended without printing their verdict** — 4, 6 and
# 7a — and one of the first round's seven did the same. The process died
# immediately after its last per-second line, with no message on a stream that
# was captured, and the next run started on time, so nothing hung. It has never
# happened on the development machine across dozens of runs. What it costs is
# visible here: the timing of the keyframe requests is gone, and the bitrate
# verdict of 7a had to be reconstructed from the tick lines. The next round
# records each run's exit code, which separates a crash from a clean exit, and
# that is the only thing that will say what this is.
#
# ---------------------------------------------------------------------------
# THIRD ROUND, 12 September 2026: two answers and one name
# ---------------------------------------------------------------------------
#
# **Both steps of the resolution scale fail on this camera, not one.** The first
# round found 960x528 killing the capture; asked again it did the same, and
# 640x352 — the only other step there is — did the same again:
#
#     video format changed  video=640x352@30  reader=640x352  error=<nil>
#     capture interrupted, restarting  error="ReadSample: HRESULT 0x80004005"
#     camera opened  format="NV12 1280x720@30"
#     [FAIL] resolution scaling: sizes seen in the stream 1280x720
#
# So on that device **the scale has nowhere to go**: every size below full is
# accepted by the reader and then refused by the camera, and each attempt costs
# a second of black and a restart at the size the network could not carry. A
# failure that happens once is an episode; this one happened four times out of
# four across two sizes and two rounds, which makes it a property.
#
# **The hope that the bottom step could be skipped to is dead**, and it was worth
# asking: a camera that refuses the middle one could have been served by going
# straight to the last. It refuses that too.
#
# **The silent deaths have a number: `-1073741819`, that is 0xC0000005, an access
# violation.** Recording the exit code was the whole point of this round, and it
# separates a crash from a clean exit, which no amount of reading the output
# could. Both runs that crashed were the two carrying `-pli`; the three without
# it finished and printed their verdicts. Across all three rounds the flag is
# 3 for 3 and everything else is 3 in 12, so it is **not only** the flag.
#
# **Nothing is printed when it happens**, and that is itself evidence: a Win32
# exception reaching the Go runtime prints `Exception 0xc0000005` and a stack,
# as this file's own crash chapter records. Silence points at a thread the
# runtime does not own — the encoder's own — but that is a hypothesis, and the
# thing that would settle it is the Windows Application log, which names the
# faulting module. It has not been read yet.
#
# **The next round stops asking two seconds before the end**, which is a designed
# experiment and not a precaution: our request racing the encoder's release and
# the encoder faulting as it is dismantled predict the same silence, and leaving
# the teardown alone removes the first of the two.
#
# The transcripts below are verbatim, in the order they were run.
#
