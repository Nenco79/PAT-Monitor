# capture reference measurement, 29 September 2026 (early morning)
# AMD Ryzen 5 PRO 6650U with Radeon Graphics, driver 32.0.21045.5002
# camera ACER HD User Facing, `pat-capture -d 40s`, three runs
#
# **This replaces the reference of 20 August**, which was taken with the build
# that still spoke Italian and with driver 32.0.21045.1000. It is in the
# history, `git show 3cc6d93:baselines/capture-amd.txt`, and it is where the
# numbers the rules quote from August live: 32-36% of the video in bursts, 37%
# with 702d929, the probe's -3.9%.
#
# **It was taken because the pipeline changed**: the simplification pass
# (907c25c..3cc6d93) rewrote the video session, the rolling windows and the
# audio sums, and CLAUDE.md asks for this file to be redone when that happens.
# The driver is not August's, so August's numbers are not the comparison. **The
# comparison is the build from before the pass, measured in the same session and
# alternated with the new one**, which is the only road that separates the code
# from the scene — the one the August round took with 702d929.
#
#                    3cc6d93 (these runs)     907c25c (before the pass)
#   video            1146 - 1165 frames       1159 - 1165 frames
#                    28.4 - 28.8 fps          28.3 - 28.7 fps
#   bitrate          2307 - 2315 kbit/s       2243 - 2312 kbit/s
#   keyframes        20                       20
#   quantiser        mean 22.2 - 22.7         mean 21.8 - 22.2
#                    p95 24 - 26, max 28-30   p95 23 - 24, max 29-31
#   video in bursts  216-246 of ~1160 (19-21%) 258-343 of ~1160 (22-29%)
#   interval median  31.2 - 31.6 ms           31.3 - 31.6 ms
#   interval p95     68 - 69.3 ms             71.1 - 80.4 ms
#   audio            1929 - 1951 Opus packets, 61-62 kbit/s, both
#   WASAPI in bursts 0-3 of ~3900 (0%), both
#   probe            2309 -> 1425             2459 -> 1598
#   (asked 1250)     2199 -> 1459             2568 -> 1500
#                    2139 -> 1509             2467 -> 1311
#
# **Identical, and one pattern that looked like a difference was the scene.**
# In the three long runs the new build started above 2500 kbit/s and dropped
# two seconds earlier, three times out of three, and its `before_kbps` was the
# lower one each time; the probe itself fired at the same moment in all six,
# 11.0 s from `capture started` to its verdict. Eight more runs of 14 s, with
# the order reversed and `-v`, gave the old build the same overshoot (4026
# kbit/s in the fourth second of one run) and the new one the old timing, and
# the two ranges overlap: `before_kbps` 2009-2481 against 2046-2582, quantiser
# mean 22.0-23.6 against 22.1-23.4. So it belongs to the start of a capture,
# not to a build. Three against three was not enough to say it, which is why
# the second set exists.
#
# **The video still arrives in pairs, and fewer of them**: 19-29% against
# August's 32-36%, for both builds alike, so it is not the code. What moved is
# the driver or the scene, and these runs cannot say which.
#
# **The bitrate probe bites, six times out of six**, at INFO level: the
# throughput follows the command, so this encoder stays on `SetBitrate` and does
# not move to the reconfiguration. The quantiser is read from the stream: over
# ~1160 frames the encoder sets 17 attributes and the quantiser is not among
# them, and the verdict says so.
#
# **The microphone is no longer granted raw mode**:
# `AUDCLNT_E_RAW_MODE_UNSUPPORTED`, so it opens in exclusive mode, 16-bit int,
# where in August it was raw, 32-bit float. Both builds met the same refusal,
# so it is the endpoint's setting and not the code; the line `audio in WASAPI
# raw mode (OEM effects bypassed): true` holds all the same, because exclusive
# bypasses them too.
#
# Variability between identical runs stays around +-30% on the delivery
# details: do not chase a single measurement.
#
# The binaries were built with plain `go build` from each commit. The
# transcripts below are the three long runs of 3cc6d93, verbatim, in the order
# they were run (1, 3 and 5 of the six).
