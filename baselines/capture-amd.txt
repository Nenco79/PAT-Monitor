# **The transcript below is verbatim, and it is in Italian**: it is the output of
# the build of that date, which spoke Italian, and a report is evidence — it is
# not rewritten afterwards. What is ours is this header, and it is here that the
# verdict lives; the numbers below do not depend on a language.
#
# **First reference measurement on this machine.** Until today there was only
# one, taken on Intel, and it did not cover the chip on which the risky
# manoeuvres are really risky: here rebuilding the encoder has already
# interrupted the capture. A reference exists to answer "has it got worse?", and
# the question is worth more where the failure is possible.
#
# It does not replace the Intel one, which stays in baselines/capture-intel.txt.
# **Two machines are not compared with each other**: different scene, different
# light, different encoder. Each is compared with itself.
#
#   video          1158 - 1162 frames, 28.2 - 28.7 fps
#   bitrate        2240 - 2279 kbit/s out of 2500 asked for
#   keyframes      20
#   quantiser      21.6 - 21.7 mean, p95 23, max 25-26, read from the STREAM
#   audio          1943 - 1975 Opus packets, 61-63 kbit/s
#   video in bursts  376-418 out of ~1160 (32-36%)
#   WASAPI in bursts 0-1 out of ~3900 (0%)
#
# **The video arrives in pairs, and it is not a fault of ours: it has always been
# so.** A third of the intervals are bursty — `min 0s`, that is two frames
# delivered at the same instant, then a gap of 67 ms. On Intel the same line says
# 0%. It is the line CLAUDE.md says to look at first, so it had to be explained
# rather than filed away: the totals meanwhile are perfect — 28.6 fps, 20
# keyframes, everything [OK] — and that is exactly how this defect hides.
#
# Verified that **it is not a regression**, by the only road that can establish
# it: rebuilding `pat-capture` from commit 702d929, that is from before the probe
# and the two separate cadences, and remeasuring on the same machine in the same
# session.
#
#                        702d929 (before)  9ef350a (now)
#   in bursts            425 out of 1140 (37%) 376 out of 1157 (32%)
#   median                       31.3 ms           31.2 ms
#   p95                          81.2 ms           80.7 ms
#   bursts               414, from 2 to 3  364, from 2 to 3
#
# Identical. The AMD encoder emits its frames two at a time, and nobody knew
# because no measurement had ever been taken on this machine. If one day that
# number really does change, now there is something to compare it with.
#
# **The bitrate probe bites here, and it is the opposite verdict to Intel's.**
# Three times out of three, at INFO level and not WARN:
#
#   asked 1250   2474 -> 1422      2489 -> 1348      2458 -> 1383
#
# The throughput follows, so it stays on `SetBitrate` and does **not** move to
# the reconfiguration — which on this chip is the manoeuvre that has already
# killed the capture. It is the first time the probe has been observed on AMD: on
# Quick Sync it declares the encoder deaf, here it absolves it. The two signatures
# really do separate, which was why the probe was written.
#
# **And here the probe costs, where on Intel it did not.** The Intel report says
# that four seconds at half bitrate out of forty would show "on an encoder that
# really does answer SetBitrate", and this is that encoder: 2370 kbit/s with the
# earlier binary against 2278 with the current one, that is -3.9% against the
# -4.4% predicted. The difference between the two columns of the comparison **is
# the probe**, not a regression.
#
# **The quantiser is read from the stream, and the attribute's absence is
# declared.** Over 1158 frames the encoder sets 17 attributes and the quantiser
# is not among them: reading seventeen of them is what proves we know how to
# enumerate them, and without that count "it is missing" and "we cannot read it"
# look alike.
#
# Variability between identical runs stays around +-30% on the delivery details:
# do not chase a single measurement.
